# ADR-0019: Deployment: origin lock, headers, backups and live checks

- **Status:** Accepted
- **Date:** 2026-10-28
- **Deciders:** project owner (Phase 12)

## Context

Phase 12 puts the app on the hosts ADR-0006 chose: Cloudflare Pages for the app with a Pages
Function proxying `/api/*`, Render's free web service for the API, Atlas's Free cluster for
data. Its work: an env guide, cold-start handling, CORS, security headers, a backup script,
live smoke tests, monitoring notes and a runbook.

Re-checking the free tiers (2026-10-28, `free-tier-limits.md`) changed two things:
- Render's free plan now allows 5 GB of outbound traffic a month (it was 100 GB), and going
  over suspends the service until the month ends.
- Render staff treat keep-alive pings as abuse.

Atlas's Free cluster still keeps no backups.

The constraints hold: free tier only, no new dependencies, everything configurable,
enforcement on the backend.

## Decision

### Only through the proxy (origin lock)

- The Pages Function (`functions/api/[[path]].ts`) adds a shared secret to every call
  (`API_PROXY_SECRET` there, `SECURITY_PROXY_SECRET` on the API, header `X-TT-Proxy`).
- The API answers nothing without it but `SECURITY_PROXY_EXEMPT_PATHS` (`/healthz`, Render's
  health check), with a 403 in the usual error shape.
- The proxy sets `X-Forwarded-For` from Cloudflare's `CF-Connecting-IP` and drops whatever the
  caller claimed. Since nothing reaches the API around the proxy, uvicorn may trust forwarded
  addresses (`FORWARDED_ALLOW_IPS=*`), and the rate limits see real clients.
- The proxy builds the target URL as a path, never resolving it, so `/api//elsewhere` can't
  leave the API host. It points redirects into the API back through itself, and answers 503
  `SERVICE_NOT_READY` when the API can't be reached, which the app shows as "waking up".
- CORS stays off: everything is same-origin.

### A production server refuses weak settings

With `APP_ENV=production`, startup fails, naming every problem, unless:
- HSTS is on;
- the proxy secret is set;
- the refresh cookie is `Secure`;
- `/docs` is off;
- logs are JSON;
- rate limiting is on;
- CORS lists only `https://` origins.

`render.yaml` (a Render Blueprint) sets these, and holds no secret: each is `sync: false`, or
generated by Render (`AUTH_JWT_SECRET`). A test fills the Blueprint's secrets with dummies and
starts it in production. Another test keeps `.env.example` documenting every setting.

### Headers for the app

- `public/_headers` gives the app's files their headers:
  - a Content-Security-Policy that allows the app's own files plus Google's sign-in button
    (`accounts.google.com/gsi/...`), with inline styles allowed for `index.html`'s first paint
    and the dialogs' scroll lock;
  - HSTS, `X-Frame-Options: DENY` and `frame-ancestors 'none'`;
  - a Permissions-Policy allowing only the app's own microphone;
  - `Cross-Origin-Opener-Policy: same-origin-allow-popups`, which Google's sign-in popup needs;
  - long, immutable caching for the content-named `/assets/*`, and `no-cache` for `sw.js`.
- `vite preview`, and so every e2e test, serves the same policy (less what needs https), so a
  page that the policy would break fails in CI first. The axe sweep is evaluated in the page
  rather than injected as a script tag, as an extension would be.

### Smaller answers

The API gzips answers of `API_GZIP_MIN_BYTES` (1000) or more for callers that accept it, since
the free host counts every byte. Sign-in answers are never compressed (`API_GZIP_SKIP_PATHS`):
they hold a token next to what the caller sent (BREACH).

### Backups from the owner's machine

- `poe backup` writes every collection as canonical Extended JSON lines, so every BSON type
  comes back exactly, gzipped and encrypted with `BACKUP_ENCRYPTION_KEY` (Fernet).
  - A database on another machine is never backed up unencrypted (`--plain` aside).
  - A manifest records the source host, counts and indexes.
  - A backup is written under a `.partial` name and renamed once complete, so a failed one
    leaves nothing.
  - The newest `BACKUP_KEEP` are kept, matched by their exact name. The one just written is
    never deleted.
  - The live database's backups have a folder of their own (`backups/production`).
- `poe restore` first opens and counts every file of the backup, so a damaged backup or the
  wrong key changes nothing.
  - It writes into empty collections, or replaces them with `--drop`.
  - It checks each count before making the indexes again (expiring ones last).
  - It says which collections it already replaced if it stops part-way.
  - It shows the backup's source and the target, and asks for that `host/database`. `--yes`
    can't be combined with `--drop` on another machine's database.
- Every maintenance command prints the host it works on. Only `poe dev` and `poe test` load the
  developer's `.env` into the environment: the others read it through the settings, under the
  real environment, so `$env:APP_ENV = "production"` reaches `environments/production.env`.
- It needs PyMongo only, not `mongodb-database-tools`.
- Backups never go to GitHub: artifacts of a public repository can be downloaded by any
  signed-in GitHub user.

### Live checks as the monitoring

- `poe smoke-live` checks the live app from outside:
  - the page's headers, a deep link, the install files and asset caching;
  - the API awake (it waits out a cold start) and its database reachable;
  - strangers refused with hardened headers, the CSRF rule, docs hidden;
  - the origin lock.
  With a test account in `SMOKE_EMAIL`/`SMOKE_PASSWORD`, it also signs in, checks the cookie's
  flags, and signs out. It never prints the password or a token.
- The `smoke-live` workflow runs it daily and by hand. A failed run emails the owner. That,
  jobs-cron's failures, Render's deploy emails, Atlas's alerts and the admin console's usage
  page are the monitoring (`deployment.md`).

### Placement

- Render: Singapore, the closest region to India. Atlas: AWS Singapore (ap-southeast-1), next
  to it.
- Render deploys `main` once its CI checks pass (`autoDeployTrigger: checksPass`).
- No keep-alive pings: the first request after 15 idle minutes waits for a cold start, which
  the app already shows.

## Consequences

- No new dependencies.
- The runbook (`docs/deployment.md`) covers the accounts, secrets, first deploy, first admin,
  GitHub secrets, live checks, backups, monitoring, limits, secret rotation and
  troubleshooting.
- Changing the proxy secret means a short window of 403s between the two redeploys.
- The API can't be called directly, even for debugging; use the app's `/api` or a local run.
- The live checks (Lighthouse on the live address, a push on Android from the cron) need the
  owner's deploy; the runbook lists them.

## Alternatives considered

- **Allowing only Cloudflare's addresses at Render**: the free plan has no firewall, and a
  Worker's outgoing address isn't fixed.
- **Authenticated origin pulls (mTLS)**: not available for a Function's calls to an outside
  host.
- **mongodump**: an extra install.
- **Backups in GitHub Actions**: public artifacts.
- **A keep-alive cron**: Render's staff treat it as abuse, and it would spend the instance
  hours.
- **Stricter CSP for styles** (nonces): Radix adds a style element at run time.
